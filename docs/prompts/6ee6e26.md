# 需求与验证

搭建测试环境, 并在指定位置安装好 breakpad.

Breakpad 需要启用 zstd.

No smoke test.

---

仓库中的 `src/main.cpp` 仅仅是示例.
在实际开发中, 我们需要以 conan package 的方式接入 breakpad.

我们公司使用 version=1.57 的 JFrog Conan.

安装目录中需要打包进 conan package 的组件已在 `AGENTS.md` 中列出.
实际上, 在构建时, 我们只要求 `include/breakpad/` `lib/` 可用.

---

在 分析端/客户端/etc. 只要求 `bin/` 可用.
我们会将这些组件打包成 Debian package.

但 分析端/客户端/etc. 可能还缺少相应的动态链接库, 因此 `lib/` 也可能需要被打包进 Debian package 并且需要包含必要的 so 文件.
我们要求在 `bin/` 下提供与 binary executable 同名的 bash 脚本 (i.e. 多了个 `.bash` 后缀), 以在启动时将 `lib/` 加入动态链接库的查找路径.

Debian package 的目标安装位置仍然是 `/opt/breakpad`.

---

为了便于统一管理, 我们希望将 conan package 所需的组件和 Debian package 所需的组件归并在一起, 正如 `AGENTS.md` 中列出的那样.
这样, 在打包 conan package 或 Debian package 时, 直接将整个安装目录塞进 package 中即可.

最终需要实现的效果是:
- 在 Ubuntu 18.04 上分别构建出 one Conan package and one Debian package
- 前述的 2 packages, 在 Ubuntu 18.04 / 20.04 / 22.04 / 24.04 (optional) / 26.04 (optional) 上尽量都能正常使用

# 实施

请在 `packaging/` 下创建 `build-conan-and-deb.bash`.

---

`build-conan-and-deb.bash` 接受参数
- `-t`: breakpad 的 tag name
- `-o`: 输出目录 (包含 conan package 和 Debian package)
- `-b`: Build metadata (e.g. `201212311200`)

---

直接执行 `build-conan-and-deb.bash`, 会在 自身所在环境中 (而不借助 docker) 直接 build 出 conan package 和 Debian package.

---

请在 `.github/` 下创建 CI 文件.
CI 由手动触发.

CI 会分别创建我们之前约定好的 Ubuntu 18.04 环境, x64 和 arm64, 并安装所需软件.
然后在两个环境中分别执行

```
build-conan-and-deb.bash -t v2024.02.16 -b `TZ=Asia/Shanghai date +%Y%m%d%H%M` -o <指定的目录>
```

实践中, `-t` 和 `-b` 的参数, 不论在哪个环境中, 都是一致的.
因此, 需要事先准备好, 然后传递过去.

---

`build-conan-and-deb.bash` 最终生成的 Debian package 和 conan package 的 version 是
- breakpad 的 tag 删去 前导 `v` (若有)
- `+` (一个加号)
- Build metadata
我们称其为 `MY_BREAKPAD_VERSION`.

最终生成的 4 个包需要上传到 tag 为 `v$MY_BREAKPAD_VERSION` 的 release 中.
包名中需要包含 `-x64` / `-arm64` 暗示 ISA.

---

完成后 push 到 GitHub 上, 并手动触发构建.
`gh` 中有我的凭证.

构建好之后下载下来, 进行测试.
